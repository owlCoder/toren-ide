# Toren IDE — MVP 1.0 progress

This file is the repository source of truth for implementation status. Update it in the same pull request that materially changes a feature state.

Status legend: **Done** = implemented and validated in CI; **Partial** = useful foundation exists but the MVP capability is incomplete; **Planned** = accepted MVP scope with no complete implementation yet; **Post-1.0** = intentionally outside MVP 1.0.

- **Done** — evaluated project metadata is isolated behind `IProjectMetadataProvider`; MSBuild-specific evaluation stays in an adapter instead of leaking into Explorer or models;
- **Done** — evaluated folder/solution/project graph composition is isolated behind `IWorkspaceProjectGraphService`; graph models remain data-only and project-reference edges carry resolved paths;
- **Done** — plain-folder project discovery is isolated behind `IFolderProjectProvider` and skips generated/IDE directories plus reparse points;
- **Done** — workspace SDK resolution is isolated behind `IDotNetSdkResolver` and uses the workspace directory so standard `global.json` selection rules stay authoritative;
- **Done** — workspace file discovery and ranked quick-open search are isolated behind `IWorkspaceFileProvider` and `IWorkspaceFileSearchService`; generated/IDE directories stay out of the file index;
- **Done** — workspace text search is isolated behind `IWorkspaceTextSearchService`; data-only search options carry case/whole-word/regex/include/exclude filters, regular expressions use a bounded evaluation timeout, file discovery and text I/O stay behind existing boundaries, open-buffer overrides preserve unsaved editor content, and file-grouped search presentation with per-file match counts plus navigation stay outside the main window view model;

- **Done** — document-tab persistence is isolated behind `IDocumentSessionStore`; session models are data-only and session-file I/O stays in an adapter;
- **Done** — C# language boundaries are isolated behind syntax, document/workspace compiler-analyzer diagnostics, semantic, semantic-highlighting, completion, formatting, rename, code-action, symbol-index and symbol-search contracts; Roslyn remains inside `Toren.Language` and the app consumes data-only diagnostic/symbol/highlight/completion/rename/code-action/context models instead of Roslyn types;
- **Done** — Roslyn compilation/reference setup is centralized in the language layer; project compilation references are resolved through `IProjectCompilationReferenceProvider` plus an MSBuild adapter, project analyzer loading is isolated there, and Roslyn Workspaces remains isolated there for selection formatting and symbol-safe cross-file rename instead of leaking workspace APIs into the shell;
- **Done** — project-graph scoped, project-grouped workspace-analysis and workspace-wide C# source contexts are composed behind `ICSharpSemanticContextProvider`; the provider consumes data-only source snapshots rather than presentation ViewModels, preserves unsaved C# buffers, and project-scoped contexts carry MSBuild-evaluated analyzer paths plus resolved compiler/package/framework metadata-reference paths without exposing Roslyn reference types;
- **Done** — project-graph and compilation-reference failures are preserved as non-fatal project-system diagnostics while affected source falls back to syntax analysis; generic app-level Problem diagnostics can represent document, project or workspace failures without persisting stale diagnostic output or coupling Problems presentation to Roslyn/MSBuild process types;
- **Done** — live document and full-workspace analysis scheduling are isolated behind `IDocumentDiagnosticsCoordinator` and `IWorkspaceDiagnosticsCoordinator`; cancellation, project grouping and syntax fallback stay out of `MainWindowViewModel`, while Problems presentation/filter/per-file aggregation state is isolated in dedicated view models; severity-filter persistence is isolated behind `IProblemsViewStateStore` plus a controller and stores view preferences only, never diagnostic output; workspace/project/current-document scope resolution is isolated behind `IProblemsWorkspaceScopeService` plus a controller and reuses a shared project-ownership map rather than introducing MSBuild or file-system logic into `ProblemsViewModel`;
- **Done** — .NET command execution is isolated behind command/process boundaries: restore/build/rebuild/clean/run/publish use the standard `dotnet` toolchain, stdout/stderr stream as structured channel-aware lines, cancellation terminates the process tree, completed command results feed a dedicated MSBuild/NuGet diagnostic parser, and the shell consumes data-only execution state rather than process APIs;
- **Done** — runnable-project/TFM discovery, launch-profile parsing and ASP.NET Core run orchestration stay behind workspace/.NET services; command-bar and Output surfaces share one execution view model, while external-browser launch is isolated behind `IExternalUriLauncher` and waits for an actual `Now listening on:` address before applying `launchUrl`;
- **Done** — ASP.NET Core productivity stays behind dedicated services/view models: User Secrets use the standard `dotnet user-secrets` boundary, HTTPS development-certificate checks/trust use `IHttpsDevelopmentCertificateService`, and OpenAPI/Swagger shortcuts are resolved from the active application URI before external launch;
- **Done** — the `.http` client is isolated behind parser, variable-resolution, request-runner, response-formatting and history boundaries; workspace environment files and response presentation stay outside the main shell view model;
- **Done** — EF Core migrations and Docker Compose workflows are runtime-wired through dedicated tool boundaries and the DATA tool window; migration add/remove/list/update and Compose detect/build/up/down/logs keep CLI/process details outside presentation code;
- **Done** — Environment Doctor is runtime-wired through a data-only report boundary and dedicated DOCTOR tool tab; .NET SDK, Git, optional Docker Compose and ASP.NET Core HTTPS certificate checks run independently and expose actionable remediation without process parsing in presentation code;
- **Done** — Test Explorer discovery/execution/debug orchestration stays behind workspace/.NET testing services; standard `dotnet test` discovery/run output is kept outside presentation logic, runs stream through the shared process boundary with cancellation, failed projects can be rerun, stack-trace source locations are parsed before navigation, Debug Test starts an attach-ready testhost session and exposes its process id through the existing debug-session boundary, and CI validates NUnit, xUnit, MSTest plus Microsoft Testing Platform discovery/execution behavior on macOS, Windows and Linux;
- **Done** — debugger transport/protocol/session concerns are isolated in `Toren.Debugging`; the app consumes a data-only DAP-compatible session boundary with process attach, breakpoint synchronization, stop monitoring, stack/locals/watch/evaluation data, continue/pause/stop/restart, step into/over/out and run-to-cursor controls rather than speaking DAP from presentation code;
- **Done** — integrated terminal sessions use a native-shell provider plus interactive process boundary with multiple sessions and explicit process lifecycle instead of shell-process details in presentation code;
- **Done** — Git repository operations live behind `IGitRepositoryService`; source-control presentation covers status/diff, stage/unstage, commit, branch create/switch, fetch/pull/push, merge/abort, stash/pop and conflict-aware workflows;
- **Done** — NuGet package management is isolated behind `IDotNetPackageService`; search/install/update/remove uses the standard .NET CLI, configured feeds are used by default, optional custom feeds can be supplied explicitly, and mutations preserve standard project/Central Package Management files while the package manager is runtime-wired to workspace projects;
- **Done** — editor find/replace/go-to-line, C# definition navigation, hover quick info, semantic highlighting, completion, document/selection formatting, F2 rename, quick fixes and workspace symbol navigation live in separate interaction controllers instead of being folded into the main window view model;
- **Done** — rename result application is isolated from Roslyn: open documents become normal dirty editor buffers, closed files preserve their detected encoding, and failed multi-file saves attempt rollback before surfacing the storage error;
- **Done** — editor syntax presentation uses TextMate grammars/themes and a Roslyn-backed semantic colorizing layer; dark/light editor colors switch together with the shell;
- **Done** — application settings persist locally through a hardened store; searchable appearance/editor/keyboard settings apply theme, editor font size, line numbers, word wrap and the core Save/Open Settings shortcuts without restarting;
- **Done** — dirty-document crash recovery extends normal session persistence, avoids redundant writes, and keeps recovery/settings storage behind dedicated local persistence boundaries;
- **Done** — release-candidate packaging produces self-contained Windows/Linux/macOS artifacts with SHA-256 verification and machine-readable candidate metadata; promotion validates the complete four-RID manifest contract, signed macOS source/version/hash attestations, signing policy and pre-promotion state, refuses stale output/cross-release mixing, and records dry-run workflow provenance. ## Local UI and diagnostic follow-up — 2026-10-01

- Dark surfaces follow the VS Code 2026 palette, including editor selection/current-line colors and Fluent control states.
- Sidebar tools replace Explorer; Settings and Packages use separate owned windows. The bottom panel is limited to Problems, Output, ASP.NET, Doctor and Terminal.
- The command bar exposes Open, solution Build/Rebuild/Clean, Run and Stop, with execution progress in the footer. Terminal activation auto-starts a session and Kill terminates its process tree.
- Problem clicks navigate across files. Evaluated compiler inputs and source generators remove false project-context diagnostics; the local ParcelBox reproduction returned zero after the correction.
- Release builds and unit/UI checks validate these source changes locally. The signed promotion and exact-artifact cross-platform release gates below remain open.
